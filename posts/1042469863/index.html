2. RESTful API 网关层详解

📍 文件位置：web-server/internal/httpserver/server.go

核心职责

  1. 协议转换：HTTP ↔ gRPC
  2. 统一认证：JWT Token 验证
  3. 路由分发：RESTful 端点 → gRPC 方法
  4. 超时控制：context 超时传递
  5. 健康检查：Kubernetes 存活探针

🔐 认证中间件实现

💡 网关层设计亮点

  • gRPC 连接池：长连接复用，避免每次请求重建 TCP 连接
  • 上下文超时传递：HTTP 请求超时自动传递给 gRPC
  • 白名单认证：灵活的公开接口配置
  • 用户信息注入：认证后用户信息全局可用

3. gRPC 业务逻辑层详解

📍 文件位置：proto/logic/v1/logic.proto + logic-server/internal/service/

📋 Protobuf 接口定义

35 个 RPC 方法，4 大模块：

模块 RPC 方法数量 核心功能
认证模块 5 Register/Login/Logout/VerifyToken/GetMyProfile
课程管理 12 Create/Update/Delete/Publish + 课时管理
购买播放 6 模拟购买 + 播放鉴权 + 已购课程列表
文件上传 1 UploadCourseAsset 流式 RPC

🚀 gRPC 流式上传（核心亮点）

分片上传流程：

  1. 前端把大文件切成 1MB chunks
  2. 客户端流式逐个发送 chunk 到后端
  3. 后端累计接收 → 调用 OSS 分片 API
  4. 所有 chunk 接收完成 → OSS 合并文件
  5. 返回最终 OSS URL

  1. 状态码标准化：ErrorCode 统一错误处理

  3. 日志追踪：每个方法入口/出口打印 DEBUG 日志
  4. 错误封装：统一 errc() / ok() 辅助函数

5. 核心技术面试问答

🔴 高频问题 - 架构篇

Q1：为什么要分成 web-server + logic-server 两层？

标准答案：

  • 关注点分离：网关层专注 HTTP 协议处理，逻辑层专注业务
  • 独立扩展：web-server 可以水平扩实例应对高并发
  • 技术异构：以后逻辑层可以换语言，网关不变
  • 安全屏障：统一在网关做认证，避免业务层出错
  • 简历加分： 这是标准的微服务网关模式！

Q2：gRPC 相比 RESTful 有什么优势？

标准答案：

  1. 性能：Protobuf 二进制序列化比 JSON 快 3-5 倍
  2. 强类型：proto 定义就是接口文档，前后端不会扯皮
  3. 流式通信：原生支持 client/server/bidirectional 流（我们的分片上传用了 client stream）
  4. HTTP/2：基于 HTTP/2，多路复用、头部压缩
  5. 代码生成：protoc 自动生成客户端和服务端代码

Q3：JWT 认证的优缺点？

标准答案：
✅ 优点：

  • 无状态，服务端不用存 session，天然支持分布式
  • 信息自包含，payload 可以带 username/role 等信息
  • 前后端、跨服务都能用

❌ 缺点：

  • 签发后不能作废，只能等过期（我们用了短期 TTL）
  • payload 只是 base64，不能存敏感信息
  • 比 session token 长，增加带宽

🟠 高频问题 - 并发篇

Q4：Go 语言在项目中怎么体现并发能力？

标准答案：

  1. goroutine 模型：每个 HTTP 请求 Gin 自动开一个 goroutine 处理
  2. gRPC 并发：同一个 gRPC 连接上可以同时跑多个请求
  3. 数据库连接池：25 个连接支持 25 个并发 SQL 查询
  4. 上下文控制：context.WithTimeout() 防止并发请求堆积

我们项目能支持多少并发？
保守估计：单实例支持 1000+ 并发用户 同时在线看视频

Q5：什么是连接池？为什么要设置 25 个连接？

标准答案：

  • 连接池 = 提前建好一批 TCP 连接，重复使用
  • 避免每次 SQL 查询都建 TCP 三次握手
  • 25 是经验值：MySQL 单实例推荐并发连接 50-100，我们服务占 25
  • 太多连接 MySQL 上下文切换开销大，太少排队等待

🟡 高频问题 - 业务篇

Q6：为什么视频要用预签名 URL，不直接访问？

标准答案：

  1. 防盗链：直接把 OSS 原始地址放前端会被人抓去盗刷
  2. 权限控制：只有买了课的用户才能生成签名 URL
  3. 时效控制：3600 秒过期，即使泄露也只能用 1 小时
  4. 计费安全：防止 OSS 流量被盗刷产生巨额账单

Q7：分片上传解决了什么问题？

标准答案：

  • 大文件支持：2GB+ 视频不会超时断开
  • 断点续传：传到一半断网了，下次继续传剩下的 chunk
  • 并发上传：前端可以并发传多个 chunk，速度翻倍
  • 内存友好：后端不用把整个大文件读到内存

🎯 面试话术模板

面试官：”介绍一下你这个项目”

标准回答模板（45 秒版）：

“这是一个在线教育视频平台，我做的后端。采用 Go 语言 开发，两层微服务架构：

  1. 上层是 Gin 做的 RESTful API 网关，负责 JWT 认证和路由
  2. 下层是 gRPC 业务逻辑服务，处理课程、用户、购买这些核心逻辑
  3. 存储用 MySQL + sqlx 连接池，文件用阿里云 OSS 分片上传

核心功能包括：用户注册登录、课程管理、视频播放鉴权。
主要技术亮点是 gRPC 流式上传 和 OSS 预签名 URL 播放鉴权。”

⚠️ 避坑提醒

  1. 不要说”我不知道” → 换成”这个地方我当时主要关注的是功能实现，具体底层原理后续有深入研究…”
  2. 不要吹牛逼 → 并发说 1000+ 就行，别说 10 万
  3. 引导面试官 → 主动提”分片上传”和”预签名 URL”，这两个是我们项目的亮点

祝面试顺利！🚀
