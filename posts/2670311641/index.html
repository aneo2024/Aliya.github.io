5.4 深度辨析：SSE vs WebSocket vs WebRTC

从 TCP/IP 协议栈看三者定位

核心澄清（面试高频考点）：
SSE 也是真正的持久TCP连接，底层是 Connection: keep-alive + Transfer-Encoding: chunked，属于 HTTP 1.1 标准的长连接机制，和 WebSocket 一样都是操作系统内核维护的 TCP Socket，不存在谁是”模拟”的！

三者定位与关系对比表

维度 SSE WebSocket WebRTC
核心定位 服务器→客户端 单向文本推送 客户端↔服务器 双向通信 浏览器↔浏览器 P2P媒体传输
连接方式 C/S 客户端-服务器 C/S 客户端-服务器 P2P 端到端直连
传输协议 TCP 可靠有序 TCP 可靠有序 UDP 为主 + TCP 备选
数据类型 仅 UTF-8 文本 文本 + 二进制 Blob 音频/视频/任意二进制
NAT穿透 ❌ 不需要 ❌ 不需要 ✅ 内置 ICE/STUN/TURN
适用本项目 ✅ 非常合适 ⚠️ 过度设计 ❌ 完全不相关

三者是什么关系？

  1. SSE ↔ WebSocket：竞争 + 互补

    • 同属 C/S 架构下解决”HTTP 一问一答缺陷”的方案
    • SSE 擅长单向状态推送（日志、行情、LLM 输出）
    • WebSocket 擅长双向交互（聊天室、协同编辑、停止生成）

  2. WebSocket ↔ WebRTC：经常配合，但完全不同层

    • WebSocket 只负责拨号阶段的信令交换
    • 连接建立后 WebRTC 直接 P2P 传输，WebSocket 就退休了

  3. SSE ↔ WebRTC：几乎没关系

    • 解决的问题域完全不重叠
    • WebRTC 是浏览器内置多媒体引擎，SSE 是文本推送协议

本项目技术选型的深度思考（面试加分项）

为什么选择 SSE 而不是 WebSocket？

  • 本项目是多阶段单向状态机输出：status → log → image → token → file → end
  • 不需要客户端中途上行指令（停止/追加问题）
  • EventSource 内置自动重连，断线续传
  • 反向代理/CDN 对 HTTP SSE 兼容性远优于 WebSocket

为什么绝对不可能用 WebRTC？

  • 没有浏览器-浏览器直连需求
  • 为了推几个 JSON 字符串引入 NAT 穿透和编解码引擎 = 复杂度 × 10

常见误区澄清：

❌ 错误认知：”SSE 是伪实时，WebSocket 才是真实时”

✅ 正确理解：本项目”伪流式”的感觉来自 multi_agent_consultation() 这个大阻塞函数，不是 SSE 技术本身。Agent 协商过程（0-20秒）是原子的，只有最后 LLM 输出才是 token 级流式。

七、架构亮点与面试要点

✅ 核心设计亮点

  1. 分层解耦：Planner → Agent → Tools 三层职责清晰
  2. 容错设计：代码执行3次自动修复 + 全局异常捕获保底
  3. 会话复用：历史视觉结果无需重新检测，大幅提升响应速度
  4. 渐进式输出：SSE状态反馈 → 日志 → 图片 → 文本 → 文件
  5. 静态文件托管：标注图片直接HTTP可访问，无需额外对象存储

⚠️ 可优化点（面试可主动提及）

  1. WebSocket补充：当前SSE单向，复杂协作场景可补充WebSocket
  2. 分布式锁：多实例部署下会话记忆需引入Redis
  3. 任务队列：图片检测可Celery异步化，避免请求超时
  4. Agent对话历史：当前GroupChat未持久化，长会话支持不足

💡 面试话术建议

基础版（主打架构设计）

“这个项目我主导了后端架构设计，核心解决了多模态输入的统一路由、Function Calling的可靠性保障、长输出用户体验三个问题。采用FastAPI + AutoGen + MCP的技术栈，实现了输入分类-Planner规划-Multi-Agent协商-工具执行的全链路。特别在Python代码执行可靠性上做了多层容错，最终把代码执行成功率从60%提升到了95%以上。”

进阶版（主打技术深度）

“在实时通信技术选型上我做了比较充分的调研。很多人以为 SSE 是”伪流式”，其实 SSE 和 WebSocket 底层都是内核维护的持久 TCP 连接，区别只在应用层协议。这个项目就是多阶段单向状态推送，SSE 足够简洁。

至于 WebRTC —— 那是完全另一个层面的东西，解决 P2P 媒体传输的，和这个场景根本不沾边。技术选型最忌讳的就是拿着锤子找钉子。”

灵魂拷问应答（必问的技术细节）

❓ 问：”既然要流式，为什么不用 WebSocket？”

✅ 答：”如果只是服务器单向推状态，SSE 有浏览器自动重连、有事件 ID，开发量只有 WebSocket 的 1/3。而且 HTTP 长连接在各种反向代理里的坑也少多了。除非我们要做用户中途点停止、或者人工介入 Agent 执行，不然 WebSocket 就是过度设计。”
