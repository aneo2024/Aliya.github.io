嗯对，大概就是做完了项目，但是完全不记得在构建项目的过程中发生了什么事情吧。

所以，拿ai整理了一下，整个开发过程中找它问了哪些问题。然后又让ai整理了一下，我可以从中学习到什么东西。

ScriptSmith 技术文档学习要点总结

基于四篇技术文档：bug-fix-report.md、changelog-2026-06-16.md、yaml-schema.md、session-fix-report-2026-06-06.md

一、后端架构与设计模式

1. 分层架构实践

  • Repository → Service → Handler 三层解耦
  • 数据访问层封装查询方法，按角色区分权限（GetByIDAndUser vs GetByID）
  • Service 层做业务编排和权限判断（如 GetTask 中 admin/user 角色分流）
  • Handler 层仅从 Gin Context 取值并调用 Service，不写业务逻辑

2. API 响应格式统一化

  • 设计统一的 {success, code, message, data} 响应结构
  • 用辅助函数（OK/ErrorBadRequest/ErrorUnauthorized 等 10 个）替代散落的 c.JSON(gin.H{...})，提升一致性和可维护性

3. 路由注册陷阱

  • RegisterRoutes() 方法写了但 main.go 没调用 → 路由永远不生效
  • 教训：路由注册要么全集中手写，要么全走自注册方法，混用容易遗漏

4. 环境变量兜底策略

  • JWT 密钥通过 getSecret() 统一入口，开发环境提供默认值 + 日志告警
  • godotenv.Load() 工作目录与 .env 位置不匹配时，尝试多个路径

二、前端工程实践

1. 认证体系全链路

  • API 拦截器：请求自动附加 Bearer Token；响应 401 自动跳登录页
  • React Context 状态管理：useAuth hook 管理 user/token/isLoggedIn/loading 四个状态
  • 初始化流程：localStorage 恢复 → /me 验证 → 失败则清空
  • 路由守卫：AuthGuard 三种状态（loading → Spin / 未登录 → 重定向 / 已登录 → 渲染）

2. 统一解包层设计

  • 前端拦截器透明解包 {success, data} 格式，response.data 原位替换
  • 关键收益：所有 service 调用方无需改动，.then(r => r.data) 返回值与改造前一致

3. 数据持久化策略

  • localStorage 草稿保存：useState 初始化时恢复，每次输入时自动保存，任务完成时清除
  • 完整数据流：用户输入 → localStorage → 刷新恢复 → 任务完成清除

4. 组件状态重置

  • 页面返回后数据残留：用 useEffect(() => { reset(); ... }, []) 在挂载时强制重置
  • 不同路由间的状态污染：navigate 前先调 reset() 清除旧状态

三、Bug 排查与调试方法

1. 多层问题叠加排查

  • 登录提示不显示的三重根因：AxiosError 只读属性 → antd v5 message context 隔离 → 401 拦截器吞错误
  • 排查思路：逐层定位，从拦截器 → 消息组件 → 特殊路由豁免

2. 编译错误定位

  • non-declaration statement outside function body：Write 工具追加内容导致旧代码残留，} 配对错误
  • 教训：覆盖文件前先 Read 确认，改完立即 go build 验证

3. 数据流断裂诊断

  • 前端调用旧 YAML 接口报 400 → 后端 ResultYAML 已不再写入
  • 死循环重定向：status === 'completed' 未重置 → useEffect 反复触发导航

4. 方法名不匹配

  • h.workRepo.GetByID undefined → 实际方法名是 Get
  • 构造函数缺少依赖注入 → 运行时 panic

四、AI 集成与 Prompt 工程

1. Prompt 参数化

  • buildStructuredPrompt 根据 format/style 注入对应中文提示词
  • 武侠风 → “江湖恩怨、武打场景、侠义精神”，动画剧本 → 动画格式要求

2. JSON 解析容错

  • extractJSON 优先匹配 [...] 数组，回退匹配 {...} 对象
  • AI 输出格式不严格时，解析层做防御性处理

3. 分层数据设计

  • 作品级角色设定（长相/年龄/性格/背景）vs 剧本级角色装扮（每集可变）
  • 角色信息同步策略：姓名作匹配键，性别/性格/背景→填空式同步，年龄/外貌→不同步

4. AI 调用条件化

  • includeNotes 开关：用户可选择是否让 AI 生成改编备注，后端据此决定 prompt 中是否包含对应 requirement

五、用户体验设计

1. 加载状态反馈

  • 三层反馈：按钮 loading + 全屏 Modal + 分阶段文字/进度条动画
  • 分阶段文字每 3 秒切换，模拟进度感，降低等待焦虑

2. 交互可发现性

  • 编辑入口从”双击才能发现”改为常驻/悬停显示编辑图标
  • 每个剧集 Tab 旁增加编辑图标，支持任意集跳转编辑

3. 超时处理

  • AI 生成请求的 axios 超时从默认 10s 提升到 120s
  • 同步等待替代异步”请稍后刷新”模式

4. 冗余清理

  • 永远为”草稿”的状态标签直接删除
  • 从未使用的页面和路由直接删除

六、数据建模与规范

1. YAML/JSON Schema 设计

  • 剧本导出采用标准 YAML 格式，定义完整的 schema
  • characters / scenes / content 各层级的字段定义、枚举值、必填规则
  • JSON Schema 用于校验和工具集成

2. omitempty 策略

  • 空值字段不出现在 YAML 中，保持输出干净

3. 内容块类型系统

  • action / dialogue / transition / sound / note 五种类型，通过 type 字段区分

七、工程流程与规范

1. 改动记录文档化

  • 每条改动记录问题 → 原因 → 方案，清晰可追溯
  • 附录列出涉及文件清单 + 变更类型

2. 测试验证清单

  • 每条修复对应明确的测试项、验证方法和预期结果

3. UI 迭代记录

  • 改编备注组件经历了 v1→v5 共 5 个版本迭代，记录每版方案和弃用原因，最终选浮动拖拽面板

4. 技术决策讨论

  • RAG 不需要（项目已有完整数据，只需语义分析）
  • 长文本分段转换（避免幻觉、保持一致性、节省 token）
  • 年龄不参与同步（每集时间线可能不同）

总览

这四篇文档覆盖了从后端分层架构、前端认证体系、AI Prompt 工程、Bug 排查方法到用户体验设计的完整技术栈。最有价值的部分是用真实项目中的踩坑经历作为案例，展示了完整的问题诊断 → 根因分析 → 修复方案 → 测试验证闭环。
